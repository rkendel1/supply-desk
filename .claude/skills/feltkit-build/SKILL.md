# FeltKit: build an application

FeltKit runs one application on one FeltDB instance per environment, exposed through AppPort. You change the
application by editing TypeScript in `feltkit/`; the dev server reloads it without reopening state.

**This skill is guidance, not authority.** Roles in `feltkit({ roles })` decide what any caller may do, on every
interface. Nothing here grants a permission.

## Project layout

```
feltkit/app.ts            the application: feltkit({ name, roles, dev, services })
feltkit/<module>.ts       functions; each export is "<module>:<export>" (tasks.ts list → "tasks:list")
feltkit/_*.ts             helpers shared by function modules (pure business rules); not loaded as functions
feltkit/_generated/api.ts generated by `feltkit dev` / `feltkit codegen`; never edit
src/                      the frontend (Vite + React)
tests/*.test.ts           run by `feltkit test`
.feltkit/<env>/           local state, the admin token, and the encrypted credential vault; never commit, never print or read them
```

## Workflow: add a feature

1. Read `feltkit/app.ts` and the module you will change. Run `npx feltkit inspect --json` for the live picture.
2. Declare data with `app.collection(name, shape, { unique?, indexes? })` (references: `s.ref(otherCollection)`). Changing a collection that already holds records: run `npx feltkit migrate --dry-run`; if it names records that would fail, add an `app.migration()` (see the feltkit-data skill); names starting with `_feltkit`, `_flow`, `_feltdb`, `_appport`, and AppPort Services' collections are reserved.
3. Write functions with `app.query` / `app.mutation`. Give each an `access` permission (or `"public"` / `"authenticated"`).
4. To expose a function to AppPort clients and agents, add `capability: { name: "<noun>.<verb>" }` **and** a `returns` schema.
   Names are lowercase `<namespace>.<operation>`, ASCII letters and digits only: no hyphens, underscores or capitals
   (`exceptions.add-evidence` fails at load; write `exceptions.addevidence` or `evidence.add`). The `returns` schema is
   the published contract and rejects undeclared fields: derive it from the collection with `s.doc(tasks)`, and project
   with `.pick(...)`, `.omit(...)`, `.extend({...})`; never restate a collection's fields in a second schema.
5. Per-record rules ("only members of this workspace") go in one `feltkit({ authorize })` hook, not in each handler: it gets `{ function, args, principal, db }` after roles and validation and returns `true` or `{ allowed: false, reason }`.
6. Grant the permission to roles in `feltkit({ roles })`. Use `npx feltkit dev`; check the dashboard's Capabilities screen.
   People sign in to a deployed app through built-in accounts, `auth: { accounts: { roles: ["member"] } }` (the starter has it; the frontend calls `useSession().signUp/signIn`), or an identity provider through `auth.authenticate`.
   Password reset and address verification: `auth.accounts.email: { from, verify? }` (Mailerport; `MAILPORT_URL`/`MAILPORT_API_KEY` in production; the client's `requestPasswordReset`, `resetPassword`, `requestVerification`, `handleRedirect`). Google, GitHub, or OIDC sign-in: `auth.providers` with a `clientId` each and the secret as `credential-ref:<id>-client-secret`; never put a client secret in code. Both need `FELTKIT_PUBLIC_URL` and `FELTKIT_AUTH_SECRET` in production (`feltkit vercel env` sets them).
7. Add or update a test with `createTestApp`; run `npx feltkit test`. Then `npx feltkit build`.

```ts
// feltkit/app.ts
import { feltkit, s } from "@feltdb/feltkit";
export const app = feltkit({
  name: "tasks",
  roles: { member: ["tasks.*"], viewer: ["tasks.read"] },
  dev: { users: [{ id: "ada", roles: ["member"] }] },
});
export const tasks = app.collection("tasks", { title: s.string(), done: s.boolean() });
```

```ts
// feltkit/tasks.ts
import { fail, s } from "@feltdb/feltkit";
import { app, tasks } from "./app.js";

export const list = app.query({
  access: "tasks.read",
  capability: { name: "tasks.list" },
  returns: s.array(s.doc(tasks)),            // the stored record: declared fields + id + __version
  handler: (ctx) => ctx.db.find(tasks, {}),
});

export const create = app.mutation({
  access: "tasks.write",
  args: { title: s.string() },
  handler: (ctx, { title }) => ctx.db.insert(tasks, { title, done: false }),
});

export const complete = app.mutation({
  access: "tasks.write",
  args: { id: s.string() },
  handler: async (ctx, { id }) => {
    const task = await ctx.db.get(tasks, id);
    if (!task) fail("NOT_FOUND", `No task ${id}`);
    return ctx.db.patch(tasks, id, { done: true });
  },
});
```

`ctx` in a handler: `ctx.db` (reads; writes in mutations, committed atomically when the handler returns),
`ctx.auth` (`principal`, `has(permission)`, `require(permission)`, `requirePrincipal()`), `ctx.services`
(see the feltkit-services skill), `ctx.environment`, `ctx.requestId`, `ctx.log`. `ctx.unsafe.feltdb` bypasses
validation and the transaction: do not use it unless the user asks and understands that.

- **Errors.** `fail(code, message)`. A valid request the current state does not allow ("only an approved invoice can
  be scheduled") is `FAILED_PRECONDITION`, not `CONFLICT` (a concurrent write) or `INVALID_ARGUMENT`.
- **Retry only what says so.** An error carries `retryable: true` when the same request can succeed again (a read
  that changed before commit, an unreachable dependency). An external API's refusal is `UPSTREAM_REJECTED`
  (`details.status`), never retryable. The full table: `npx feltkit docs guarantees`, section Errors.
- **Approval.** `app.mutation({ access: "payments.send", approval: "required", ... })`: agents, services and API keys
  holding the permission can only propose it; it runs after a person who may perform it approves, as the proposer.
  People call it directly. Use it for irreversible effects you would not let an agent take alone.
- **Authority first.** A caller without a function's `access` gets `FORBIDDEN` before its arguments are checked. An
  agent that gets `FORBIDDEN` lacks the authority: hand the step to a person; do not retry with other input.
- **Services run as the caller.** Every role that calls a function needs the service permissions the function uses
  (`ctx.services.configuration.get` in a mutation → `configuration.read` on each calling role).
- **Effects that announce the change**: `ctx.afterCommit.notifications.send(...)`, `.webhooks.emit(...)`,
  `.jobs.enqueue(...)` happen only if the mutation commits (recorded in its transaction, performed after it).
  `ctx.services.*` effects happen even if the commit is later refused.
- **A business audit trail**: `export const events = app.auditTrail("events", { subjects: ["invoice"] as const })`,
  then `await events.record(ctx, { subject: "invoice", id, type: "invoice.approved", data })` next to the change, and
  `events.history(ctx, "invoice", id)` to read it in order. Each event has the actor (or `anonymous`), the request
  id and a per-subject `seq`, and commits with the change. Don't build your own (docs/TRANSACTIONS.md §9).
- **Ordering any other append-only log** written in the same transaction: ``seq: await ctx.db.sequence(`audit:${invoiceId}`)``
  and `orderBy: [{ field: "seq", direction: "asc" }]`. Never order by `Date.now()`: several writes share a millisecond.
  Order is per stream (the name): one stream per subject, so unrelated writers never contend. Writers to one stream
  serialize (`CONFLICT`); add `retry: { sequenceConflicts: 3 }` to the mutation to have it re-run instead, if its
  handler is safe to run again.

## Existing APIs and model decisions

Connect an HTTP API the user already runs as AppPort capabilities (never call `fetch` from a mutation):

```ts
export const payments = app.integration("payments", {
  baseUrl: { env: "PAYMENTS_URL", development: "http://127.0.0.1:4010" },
  credential: "credential-ref:payments",            // value: Studio → Integrations → Set key, or FELTKIT_CREDENTIAL_PAYMENTS; never in code
  operations: {
    create: { method: "POST", path: "/payments", input: { invoiceId: s.string(), amount: s.number() }, output: s.object({ id: s.string() }),
              effect: "consequential", access: "payments.write", idempotencyHeader: "Idempotency-Key",
              verify: { operation: "lookup", input: { invoiceId: { $input: "/invoiceId" } }, expect: [{ at: "/status", equals: "paid" }] } },
    lookup: { method: "GET", path: "/payments/by-invoice/{invoiceId}", output: s.object({ status: s.string() }), effect: "observation", access: "payments.read" },
  },
});
```

A consequential call whose outcome is unknown is never re-sent; declare `verify` so it can be settled from the API.
Operations are AppPort capabilities: they are called through AppPort (agents, other apps, a frontend's
`POST /appport` request with the session token), not from a query or mutation (`ctx` has no integration API).
React to a result inside the app with `onOutcome: "<module>:<mutation>"` (runs as the caller with the call record).
To let the environment's model choose a next step, start a decision from a mutation with the options you allow:
`ctx.agent.start({ objective, decision: { question, options: [{ id, label, capability?, input? }] } })`.
The choice is a proposal; consequential options wait for a person. See `examples/invoices` in the FeltKit repo.
`ctx.agent` ties the app to a FeltKit server: an AppBoundry artifact refuses it (see Portability).

**Choosing the model and its API key.** The starter enables every AppPort Service (files, notifications,
configuration, apiKeys, webhooks, jobs, schedules, intelligence; each configured in Studio → Services → Manage) and
gives the dev user Ada an `admin` role (`intelligence.*`, `credential.*`, `configuration.*`, `apikeys.*`,
`webhooks.*`, `jobs.*`, `schedules.*`) next to `member` (which includes
`feltkit.agent.*`, so Studio's Agent screen works as Ada). The user picks a provider and model and types the API
key in **Studio → Models**, saves, and presses **Test**; or, in their terminal,
`npx feltkit model set --provider anthropic --model <id> --api-key-stdin`. The key is stored by FeltKit's
credential custody (an encrypted vault outside FeltDB in development; `FELTKIT_CREDENTIAL_<ID>` overrides it and is
the only source in production). Never write a key into `feltkit/`, `.env` files you create, tests, or a reply, and
never ask the user to paste one into the chat (see the feltkit-services skill). A role that may store keys needs
`credential.store`; keep viewers and agents without it.

## Testing

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { createTestApp } from "@feltdb/feltkit/testing";
import { api } from "../feltkit/_generated/api";

test("a member completes a task", async () => {
  const app = await createTestApp();
  try {
    const id = await app.as("ada").mutation(api.tasks.create, { title: "x" });
    await app.as("ada").mutation(api.tasks.complete, { id });
    await app.restart(); // same state, new runtime: proves durability
    assert.equal((await app.as("ada").query(api.tasks.list)).length, 1);
  } finally {
    await app.close();
  }
});
```

Each test app gets an isolated FeltDB instance. Test denials too (`app.as("viewer")` should be refused writes).

**Callers in tests.** `app.query(...)` / `app.mutation(...)` on the test app itself are **anonymous**: no session,
like a visitor on a public page. Use that for `access: "public"` functions. `app.as({ id, type: "user", roles: [] })`
is a *signed-in* account with no roles, a different caller: a staff-only function refuses it with FORBIDDEN, while
it refuses an anonymous caller with UNAUTHORIZED. `app.as(who, { session: false })` is a known principal without a
session. An anonymous mutation can't stage `ctx.afterCommit.notifications/webhooks/jobs` (they run as the caller);
stage `ctx.afterCommit.agent(name, input)` for a declared `app.agent` instead.

## Portability (AppBoundry)

`npx feltkit build --target appboundry` compiles the app into `<name>.app` (runs without the project or FeltKit). It
refuses, naming file and line: `ctx.agent`, `ctx.unsafe`, `app.integration`,
`auth.authenticate`, Node built-ins, and locale-dependent code (`Intl`, `toLocaleString`, `localeCompare`: the
artifact has no locale data; format for people in the frontend). It omits Studio, `/mcp`, API keys, schedules and
webhook delivery. A plain `feltkit build` prints the same list as a warning. If the user wants the artifact, avoid
these from the start, and test it with `createArtifactTestApp("<name>.app")` from `@feltdb/feltkit/testing` (same
`as(who).query/mutation` calls). Serve it with `npx @appport/appboundry run <name>.app` (an app with built-in accounts
also needs `--accounts operator-sessions`: people then get sessions from the operator).

## When to stop and ask

- Changing roles or `access` (it changes who can do what everywhere, including agents and API keys).
- Renaming the application (`name` selects the FeltDB namespace: a rename starts from empty state).
- Deleting collections or data, or using `ctx.unsafe.feltdb`.
